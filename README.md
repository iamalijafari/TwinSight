# TwinSight — by BridgeX

**پیش از انتشار، مسیر اثر تغییر را از سرویس‌ها تا مشتری ببینید.**

TwinSight یک MVP محلی از دوقلوی نرم‌افزار سازمانی است؛ با ASP.NET Core / C# و JavaScript ساده، بدون دیتابیس و بدون وابستگی frontend در زمان اجرا. نام محصول طبق درخواست شما **TwinSight** است؛ BridgeX نام تیم است.

> داده‌ها و سازمان نمونه کاملاً ساختگی‌اند. موتور پیش‌فرض قواعد ثابت دارد، نه مدل آموزش‌دیده. «شاخص ریسک» احتمال آماری نیست. شکل زمانی، تأخیر و تعداد کاربران در معرض چالش فرض‌های نمایشی‌اند. اتصال واقعی Jira/GitHub، دریافت زندهٔ رخدادها و پیش‌بینی اعتبارسنجی‌شده در این نسخه وجود ندارد.

## اجرای اصلی با .NET

پیش‌نیاز: .NET 8 SDK. از ریشهٔ این بسته:

```bash
dotnet run --project src/TwinSight --urls http://127.0.0.1:5080
```

آدرس: <http://127.0.0.1:5080>

در macOS/Linux می‌توانید `./start-demo.sh` و در Windows فایل `start-demo.cmd` را اجرا کنید. حالت اجرا در سربرگ باید `‎.NET API · DEMO` باشد. پکیج NuGet شخص ثالث نیاز نیست؛ SDK باید framework مربوط را داشته باشد. سرویس محلی را متوقف و دوباره اجرا کنید تا نمونه‌های حافظه پاک شوند؛ پس از آن مدل را در رابط دوباره بسازید.

## دموی جایگزین بدون .NET

برای دیدن رابط و شبیه‌سازی JavaScript با Python 3:

```bash
python3 -m http.server 8080 --bind 127.0.0.1 --directory src/TwinSight/wwwroot
```

آدرس: <http://127.0.0.1:8080>

سربرگ `OFFLINE JS · DEMO` و پیام حالت آفلاین نمایش داده می‌شود. این حالت API سرور C# را اجرا نمی‌کند. باز کردن مستقیم `index.html` با `file://` کافی نیست چون ماژول‌ها و فایل داده باید از HTTP بارگیری شوند. اینترنت برای دموی پیش‌فرض لازم نیست.

## مسیر ارائهٔ نمونه

1. چهار منبع نمونه را انتخاب کنید و «ساخت مدل زنده» را بزنید. GitHub و حداقل یک منبع دیگر لازم‌اند. «زنده» در این دمو یعنی بازسازی دستی snapshot؛ اتصال پیوسته وجود ندارد.
2. سناریوی «درگاه پرداخت» را اجرا کنید. حالت پیش‌فرض: مهاجرت، Payment، انتشار ۱۰۰٪، تست ۴۵٪ و بدون انتشار تدریجی.
3. در روز ۷، شاخص اوج فرضی **۵۹٫۹ از ۱۰۰** دیده می‌شود. روی Analytics بزنید: مسیر `Payment → Orders → Analytics` و شواهد نمونه قابل بررسی‌اند. پیکان، جهت انتقال اثر است؛ به معنای جهت فراخوانی API نیست.
4. بین «امروز» و «پس از تغییر» جابه‌جا شوید؛ در خط زمانی روزهای دیگر را بررسی کنید. پخش و توقف نیز در دسترس است.
5. «نگه‌داشتن برای مقایسه» را بزنید؛ انتشار تدریجی را فعال کنید و دوباره شبیه‌سازی کنید. شاخص اوج **۳۷٫۱** می‌شود. کاهش ناشی از فرض ضریب ۰٫۶۲ است، نه نتیجهٔ مشاهدهٔ عملیاتی.
6. گروه‌های مشتری، مسیرها، فرض‌ها و اقدامات پیشنهادی را بررسی کنید. گزارش JSON شامل snapshot مدل، نتیجه، روز انتخاب‌شده و سناریوی مقایسه را دریافت کنید.
7. انتخاب یک منبع را تغییر دهید: نتیجه و مدل باطل می‌شوند و ساخت مجدد لازم است. تغییر تنظیمات فرم نتیجهٔ موجود را با برچسب «اجرای قبلی» حفظ می‌کند تا آن را با نتیجهٔ تازه اشتباه نگیرید.

## هوش مصنوعی اختیاری و نقش واقعی آن

بدون کلید، همهٔ جریان‌های اصلی دمو کار می‌کنند و سیستم دربارهٔ وجود مدل آموزش‌دیده ادعا نمی‌کند. با تنظیم کلید روی سرور، دو مسیر اضافه می‌شوند:

- **تفسیر متن تغییر:** LLM توضیح آزاد کاربر را همراه معماری و شواهد منابع انتخاب‌شده می‌خواند و سرویس‌های مستقیماً تغییرکرده، نوع تغییر و استدلال مستند پیشنهاد می‌دهد. خروجی با JSON Schema محدود و در سرور اعتبارسنجی می‌شود. پیشنهاد تا کلیک «تأیید و اعمال پیشنهاد به فرم» چیزی را تغییر نمی‌دهد. سپس کاربر شبیه‌سازی را اجرا می‌کند.
- **روایت نتیجه:** توضیح فارسی برای نتیجهٔ موجود، با محدودیت عدم تغییر اعداد و تأکید بر کنترل انسانی. این متن هم نیازمند بازبینی است؛ جدول‌ها خروجی قواعد عددی دمو هستند.

نمونهٔ تنظیم در Linux/macOS، با کلید خودتان:

```bash
export TWINSIGHT_OPENAI_API_KEY='YOUR_KEY'
export TWINSIGHT_OPENAI_MODEL='gpt-4.1-mini'
./start-demo.sh
```

در PowerShell:

```powershell
$env:TWINSIGHT_OPENAI_API_KEY = 'YOUR_KEY'
$env:TWINSIGHT_OPENAI_MODEL = 'gpt-4.1-mini'
dotnet run --project src/TwinSight --urls http://127.0.0.1:5080
```

فایل `.env.example` فقط نمونه است؛ برنامه فایل `.env` را خودکار بارگیری نمی‌کند. کلید فقط روی سرور مصرف می‌شود و به مرورگر فرستاده نمی‌شود. فقط هنگام درخواست کاربر، متن تغییر و زمینهٔ ساختگی انتخاب‌شده به OpenAI ارسال می‌شوند؛ درخواست API ممکن است هزینه داشته باشد. مدل انتخابی باید Chat Completions و Structured Outputs را پشتیبانی کند. این مسیر در محیط تحویل با سرویس واقعی اجرا نشده است.

## بررسی‌ها

Node.js 22 یا جدیدتر برای آزمون‌های بدون وابستگی:

```bash
npm test
npm run test:ui
```

آزمون‌های C#، ساخت و هم‌ارزی دو موتور:

```bash
dotnet build src/TwinSight/TwinSight.csproj
dotnet run --project tests/TwinSight.Checks
```

سرور اصلی را در ترمینال دیگر اجرا کنید، سپس:

```bash
npm run test:api
```

آزمون مرورگر و تولید تصاویر برای بررسی بصری:

```bash
npm install
npx playwright install chromium
npm run test:browser
```

`TEST_URL` آدرس آزمون API/مرورگر را تنظیم می‌کند؛ پیش‌فرض `http://127.0.0.1:5080` است. آزمون مرورگر می‌تواند روی دموی Python نیز اجرا شود؛ آزمون API فقط روی .NET معتبر است. تصاویر در `qa/` ذخیره می‌شوند؛ خودکار بودن آزمون به‌تنهایی کیفیت بصری را ثابت نمی‌کند، تصاویر باید دیده شوند.

**وضعیت واقعی تحویل:** ۸ آزمون موتور JavaScript شامل ۶۴۰ ترکیب تنظیمات و ۳ آزمون جریان رابط با DOM آزمایشی موفق شدند. بررسی نحوی JavaScript و بررسی ساختار فایل‌های محلی موفق بود. .NET SDK و Chromium در محیط ساخت موجود نبودند؛ ساخت/اجرای C#، API واقعی، روایت/تفسیر AI واقعی، نمایش در مرورگر و QA بصری واکنش‌گرایی هنوز تأیید نشده‌اند. جزئیات در [docs/TEST-REPORT.md](docs/TEST-REPORT.md) آمده است. workflow آمادهٔ GitHub وجود دارد، ولی اجرا نشده است.

## حدود MVP

این نسخه برای نمایش محلی تک‌کاربره است: احراز هویت، تفکیک سازمان‌ها، ذخیرهٔ پایدار، اتصال منابع واقعی، واردکردن فایل، SLA، مدیریت کلید سازمانی و مدل پیش‌بینی کالیبره ندارد. داده در حافظه/صفحه نگه داشته می‌شود؛ بارگذاری مجدد صفحه مدل مرورگر را پاک می‌کند. سقف نمونهٔ سرور ۱۰۰ مدل و ۵۰۰ شبیه‌سازی در هر اجراست. پیشنهاد کاهش ریسک، تأیید انتشار محسوب نمی‌شود.

برای تبدیل به محصول سازمانی باید connectorهای read-only، کیفیت/تازگی داده، حریم و دسترسی، ثبت بازخورد، replay رخدادهای تاریخی و اعتبارسنجی پیش‌بینی روی پیامدهای واقعی اضافه شوند. جزئیات و قواعد قابل بازبینی در [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) آمده است.
